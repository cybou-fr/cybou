# Peer-to-peer transport target

CYBOU P2P transports finalized history and encrypted content. Transport
discovery is never a trust anchor.

The official DEV VPS target is a bootstrap relay/cache, not a PoA finalizer or
storage provider. The genesis-key holder finalizes from the Central Authority
desktop. See [`04_NETWORK_BOOTSTRAP_AND_GENESIS.md`](04_NETWORK_BOOTSTRAP_AND_GENESIS.md).

CYP2 v3 runs over TCP protected by TLS 1.3 with the configured
`X25519MLKEM768` group and has no plaintext fallback. Providers prove their
service key and operation-accepting peers prove the genesis-bound PoA key over
the TLS exporter and both HELLOs. See [`CYP2_TRANSPORT_V3.md`](CYP2_TRANSPORT_V3.md).
Ordinary peers do not receive a canonical service identity.

## Finalized block synchronization

Peers announce/request finalized blocks. Every receiving full node independently
verifies:

```text
network
height / parent
block ID
PoA certificate
operation validity
state transition
state root
```

Only verified PoA-finalized history becomes canonical.

## Operation submission

CYP2 is the only node transport: sync, gossip, operation submission and chunk
transfer. The legacy CYB1/CYBO TCP block feed is removed. Headless finalizer
and provider commands remain for isolated LAB/testing; they are not the
official DEV VPS topology.

Unfinalized operations remain local to their origin and designated finalizer.
There is no distributed canonical pending-operation pool.

The origin retains exact signed bytes for idempotent retry while outcome is
uncertain.

In the target architecture, a client sends exact operation bytes to the
authenticated bootstrap relay, which forwards them over the Central
Authority's authenticated outbound session. Bootstrap does not advertise
`CAP_ACCEPT_OPERATIONS` as a finalizer and does not maintain a durable shared
pending pool. An explicit Authority rejection is a rejection; when the
Authority is unavailable, the client retains exact signed bytes for retry.
This relay path is not implemented by the current CYP2 service.

## Chunk transport

Providers expose the active content-addressed profile:

```text
PUT_AUTHORIZED_CHUNK
GET_CHUNK_BY_ID
GET_CHUNK_AUTHORIZATION_PROOF
```

A provider accepts PUT only after it verifies:

```text
RootPublication is in its canonical finalized history
ChunkID is authorized by the publication Merkle root
BLAKE3(bytes) == ChunkID
local capacity/policy accepts the obligation
```

GET returns encrypted stored bytes; the requester verifies ChunkID before
decryption/tree processing.

`GET_CHUNK_AUTHORIZATION_PROOF` takes a finalized publication OperationID and
candidate ChunkID. A provider returns its stored leaf index and Merkle siblings
only when the admitted encrypted blob is present and the proof still verifies
against that publication. This lets a client rebuild local placement metadata
after losing its Application DB without guessing child-tree membership or
changing canonical state.

## Provider identity

A peer that advertises `CAP_STORAGE` must prove a stable provider key in the
handshake. It sends one `PROVIDER_PROOF` frame with its hybrid Ed25519 +
ML-DSA-44 public key and signature over a transcript containing the TLS
exporter and both HELLO messages:

```text
"CYBOU/CYP2/PROVIDER-PROOF/v1" || TLS_exporter || signer_HELLO || verifier_HELLO
```

so a proof cannot be replayed into another session or network. A missing or
invalid proof fails the handshake.

```text
ProviderID = BLAKE3("CYBOU/PROVIDER-ID/v1" || ed25519_pub || ml_dsa_pub)
```

The key is the node's own `STORAGE_PROVIDER` key role, kept beside provider
data (`storage/provider.key`) and never derived from an Identity mnemonic.
Storage calls go only to a session that proved the expected ProviderID.
Placement records ProviderID plus the last known endpoint, and the remote
replica target counts distinct ProviderIDs, never address:port. ProviderID is
local operational identity; it is not a registry entry, not anti-Sybil proof
and carries no consensus weight.

## Provider discovery and clean recovery

Provider placement is operational metadata, not canonical recovery state.

A clean client that knows a RootChunkID may query multiple discovered
storage-capable peers for that ChunkID until a valid copy is found. This simple
fan-out/failover model is sufficient for the initial small network; a DHT or
global provider directory is not a Beta prerequisite.

## Advisory Validation

Validation is optional signed evidence, not a CYP2 role or canonical message.
Any full node may produce an opinion; recipients verify and assess it locally.
It does not affect PoA, state execution, finality, or chunk admission. See
[`VALIDATION.md`](VALIDATION.md).

```text
network validated != PoA-finalized
```

An attestation should bind the network, operation and finalized base it
describes. PoA remains the sole finalizer.

Do not reintroduce BFT or a competing canonical chain.

## Resource rules

Bound:

- frame size;
- request concurrency;
- tree depth/chunk count;
- reconstruction output;
- provider capacity;
- per-peer connection, operation, and byte admission before expensive
  verification, using local policy only.

Peer-provided addresses and discovery results are hints only.
