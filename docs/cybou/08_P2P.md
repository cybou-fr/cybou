# Peer-to-peer transport target

Status: **Active P2P transport specification**.
This document defines CYP2 v4 transport, peer discovery, direct mesh topology,
block synchronization, candidate operation relay, Validation signature propagation,
and storage transfer.

---

## 1. Network topology

CYBOU runs over a direct P2P mesh:

- **Initial discovery**: Nodes connect to the known official bootstrap rendezvous endpoint to discover active peers.
- **Bootstrap role**: Bootstrap is an ordinary CYBOU full peer running the same executable and CYP2 protocol. It has no special consensus role, no `CAP_BOOTSTRAP` flag, and is not a traffic intermediary.
- **Direct mesh**: Discovered full nodes establish direct CYP2 v4 connections with each other.
- **Trust**: Network identity is pinned by the compiled Network Public Key (`NetworkID`). Genesis is signed offline by the Network Private Key. PoA finality is proved by the genesis-authorized PoA key.
- **Sovereign admission**: Public inbound and outbound P2P connections are strictly restricted to French IP space, failing closed on missing Geo data. See [`37_FRANCE_SOVEREIGN_NETWORK_POLICY.md`](37_FRANCE_SOVEREIGN_NETWORK_POLICY.md).

CYP2 v4 runs over TCP protected by TLS 1.3 with the post-quantum `X25519MLKEM768`
key exchange group. Plaintext fallback is prohibited.

---

## 2. Finalized block synchronization

Full nodes announce and gossip finalized blocks across the mesh.
Every receiving node independently validates the block structure, hybrid PoA certificate,
all operation state transitions, and recomputed state root.
Only verified finalized blocks advance canonical local state.

---

## 3. Operation relay

There is no distributed mempool. Operations propagate hop-by-hop across ordinary peers:

```text
every full node:
    receives
    verifies encoding, Identity signatures and authorization
    independently executes the candidate against its finalized state
    accepts or rejects locally
    relays only accepted candidates
```

Origin retains the exact signed operation until finality. Each node keeps
accepted candidates in one bounded volatile pool; a PoA node produces blocks
from that same pool. There is no distributed mempool and no canonical pending state.

- Any node may advertise `CAP_OPERATION_RELAY`.
- A rejected candidate is never relayed.
- Loop suppression uses a bounded seen-ID cache; finalized operations are purged.
- Acknowledgments between relays are hop-by-hop notifications, never guarantees of finality.

---

## 4. Validation signature propagation

Operations propagate with zero or more Validation signatures, carried by a
separate `VALIDATION_ATTESTATION` gossip message. See [`VALIDATION.md`](VALIDATION.md).
- Only a node whose local Identity has finalized AUTH > 1,000,000 and which
  itself accepted the operation may originate one.
- Receiving peers independently validate the operation, then verify
  eligibility against their local finalized state and the signature.
- A Validation signature does not authorize relay of an otherwise invalid operation.
- Peers enforce rate limits, one signature per AccountID per operation, and bounded caches.

---

## 5. Storage chunk transport

Nodes advertising `CAP_STORAGE` authenticate their `STORAGE_PROVIDER` key during
the CYP2 handshake, establishing a session `ProviderID = BLAKE3(...)`.

Providers support:
- `PUT_AUTHORIZED_CHUNK`: accepted only after verifying canonical RootPublication finality and Merkle authorization proof.
- `GET_CHUNK_BY_ID`: serves stored encrypted bytes keyed by BLAKE3 ChunkID.
- `GET_CHUNK_AUTHORIZATION_PROOF`: returns Merkle audit path for application state rebuild.
