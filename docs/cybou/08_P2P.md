# 08 — P2P network

Implementation status: the native DEV runtime uses a bounded TCP endpoint for
finalized-block retrieval and one-operation submission. A separate native
`src/cybou/p2p/` session layer now has bounded frames, a persistent TCP
connection, HELLO with NetworkID/finalized height/tip/capabilities, and
PING/PONG. HELLO advertises block-serving and operation-acceptance capabilities;
the session checks them before requests or service. It rejects wrong-network
peers and limits each read/write to five
seconds. An outbound peer manager now uses the runtime's verified NetworkID and
finalized status to maintain up to eight explicitly configured, persistent
sessions, reject duplicate endpoints, and drop peers that fail a health ping.
The DEV producer can now listen on a separate CYP2 port. `p2p-probe` checks
health and `p2p-sync` retrieves finalized blocks through one persistent
connection, using bounded 4 KiB frames and a 32 MiB/30-second transfer limit.
The 30-second deadline covers the full request/response on the client and the
full block send on the producer, including every chunk. Peers advertising
block inventory support answer `GET_BLOCKS` with up to 32 consecutive
`(height, BlockID)` entries in `BLOCK_INV`. The observer requests each
announced block with `GET_BLOCK` and rejects it if its verified BlockID does
not match the inventory. Peers without the capability continue using
`GET_BLOCK` directly. The inventory is a transport hint; local state and BFT
certificate verification remain required.
`p2p-follow` keeps an observer connected to one explicit peer, polls for new
blocks, and retries after a transport disconnection. It stops on a failed
handshake or block verification.
`p2p-follow-peers` accepts up to eight explicit numeric endpoints, tries other
peers when one is unavailable, and excludes a peer after handshake or block
verification failure. Malformed frame headers, invalid block metadata, and
invalid chunks also exclude that peer. A connection that closes or times out
during a transfer is retried as temporarily unavailable. A peer that closes
before HELLO is retried; a malformed HELLO frame or a valid HELLO with the
wrong NetworkID is rejected. HELLO must contain a nonzero tip; at height zero
that tip must match the trusted genesis block ID. If a local historical block
exists at the height announced in HELLO, its ID must match the announced tip.
The same trusted-chain check applies before the listener serves an inbound peer.
Every accepted block still passes local finality and state checks. At the
height advertised in HELLO, the received finalized block
must also match the peer's advertised tip. Explicit endpoints remain bootstrap
seeds; peers advertising discovery support exchange bounded numeric IP/port
lists, which are routing hints only and do not establish consensus trust.
On nodes with a public-like listener, generic discovery rejects RFC1918 IPv4,
IPv6 unique-local, loopback, and link-local targets. Private listeners can use
private discovery hints, while operator-configured explicit validator peers
may use private addresses regardless of listener scope.
If a peer reports no block at a height it advertised in HELLO, the observer
disconnects and retries it later while trying other peers. A genuine missing
next block beyond the advertised height keeps the session open. After a peer
provides a batch, the observer starts its next pass with that peer instead of
waiting for every other configured endpoint in the same pass.
The observer commits each block only after canonical state and BFT finality
verification. CYP2 can also submit one canonical operation (up to 128 KiB)
in bounded frames within a 30-second send/acknowledgment deadline and return a
checked OperationID and admission status.
Authority admission now uses one `OperationPool` for local and inbound CYP2
operations. It deduplicates by OperationID, validates the complete pending
candidate against the current finalized state, and bounds the pool to 256
operations and 8 MiB of serialized operations. Each source IP is limited to
32 pending operations and 1 MiB. Successful block commits revalidate the
remaining pending operations against the new head. These limits are local
resource controls, not consensus parameters. CYP2 peers advertising the
operation-inventory capability now negotiate `OP_INV → GET_OP → OP`: a peer
requests the bounded serialized operation only when its local pool and
finalized-operation index do not already contain the OperationID. The existing
`OP_META/OP_CHUNK` submission remains available to peers without that
capability. Each session handles one inventory exchange at a time with a
30-second transfer deadline. An authority keeps a bounded local record of
recently admitted operations (up to 256 operations and 8 MiB) so a block
finalized before the next fanout pass does not erase its announcement. It
offers each OperationID to every connected accepting peer
that supports inventory negotiation.
`cybou-node serve` accepts an optional peer file after the CYP2 port and runs
this fanout in a separate worker, with at most eight configured outbound peers
and 16 new offers per peer per pass. It remembers offered OperationIDs per
connection, reconnects after a delay, and drops the oldest records when the
local gossip bound is reached. The pending pool has its own admission limits.
The same worker offers up to 16 recent finalized `(height, BlockID)` entries
per peer per pass. A receiver requests block bytes only for its next height,
then commits through the ordinary state and BFT certificate checks. Duplicate
announcements are acknowledged without transferring block bytes; a gap is
deferred for the existing sync path. The sender retains at most 32 recent
block announcements in memory. This is an initial explicit-peer gossip path;
The same CYP2 worker now sends queued proposal and vote messages for
multi-validator consensus. On a new outbound connection it also replays the
current round's local proposal, prevote, and precommit, if available. An N>1
validator refuses to start without a CYP2 listener and at least N-1 distinct
peer endpoints. Socket tests cover round rotation with an offline
leader, catch-up, reconnect, duplicate/conflicting prevotes, runtime restart
after prevote/precommit, and subsequent heights' finality. The four-process
smoke also covers OS-process restart, validator churn, and a five-round
partition pause before recovery. Separate-host/VPS fault injection,
long-duration partitions, and independently operated validator deployments
remain open.
`p2p-submit-peers` tries up to eight explicit numeric endpoints from a peer
file and stops on the first accepted, already-pending, or already-finalized
acknowledgment. It uses the same bounded CYP2 operation transfer; the peer
file supplies routing only. The CLI distinguishes a validator's explicit
rejection from no reachable accepting peer (`unavailable`) and a lost
acknowledgment after attempting delivery (`unconfirmed`).
The authority indexes OperationIDs atomically with finalized blocks, so a
retry of an indexed finalized operation receives `ALREADY_FINALIZED` regardless
of its operation type. An AccountCreate already present in history without an
index is checked against its exact finalized operation before receiving that
status; a different operation for the same AccountID is rejected.
`operation-status` scans locally stored finalized blocks by OperationID and
reports the verified block height, operation index, and BlockID. A missing
historical block produces `history-unavailable` rather than `not-found`.
Admission is not finality. The DEV listener handles up to eight concurrent
incoming sessions with one bounded worker per peer; excess connections close.
NodeRuntime owns a manager when a CYP2 endpoint is configured; operation
submission and finalized-block sync then use that session. `CybouNodeService`
owns common runtime startup, the desktop observer's network maintenance and
verified sync workers, and the authority block-feed/CYP2 listeners, consensus scheduler,
peer gossip, and historical catch-up loop. CLI commands parse configuration
and delegate runtime/network lifecycle to this service. The Qt desktop uses
observer mode and connects to the compiled DEV CYP2 bootstrap by default
(`51.255.46.58:29461`). `CYBOU_DEV_P2P_HOST` and `CYBOU_DEV_P2P_PORT` override
that seed. The observer maintains up to eight outbound CYP2 sessions, discovers
and retries peers, syncs verified blocks with bounded batches, and fans out
recent blocks. It can also accept inbound
CYP2 sessions when `CYBOU_DEV_P2P_LISTEN_PORT` is set; the default bind host
is `127.0.0.1` and can be changed with `CYBOU_DEV_P2P_LISTEN_HOST`. Its own
listener endpoint is excluded from discovery. Set
`CYBOU_DEV_LEGACY_BLOCK_FEED=1` only to use the temporary CYB1 block-feed
fallback for diagnostics; normal desktop startup uses CYP2.
Multi-peer sync treats HELLO height as a connection-time snapshot: an
up-to-date response from one peer does not prevent checking the remaining
connected peers. A peer protocol failure removes and temporarily backs off
that peer while the observer continues with its other sessions. The desktop
network worker stops for local state/network-definition failure or explicit
shutdown, not because one remote peer sent invalid data.
Observer maintenance separates cadence from block-sync passes: peer discovery
is attempted at most once per minute and queries at most one session per pass;
health pings run at most once per 15 seconds and cover one rotating peer per
pass. This bounds maintenance round trips while eventually visiting the full
connected set. Reconnect backoff distinguishes temporary connection failures
(5 seconds doubling to 5 minutes), malformed/protocol peers (30 minutes doubling
to 24 hours), and a valid HELLO for another NetworkID (24 hours, cleared when
the runtime restarts after correcting network configuration). A successful
connection or sync resets the endpoint's retry history.
TCP connection setup now has a five-second deadline. A
compiled-in DEV bootstrap address locates the authority but supplies no
consensus trust. The gossip worker queries connected discovery-capable peers
and adds returned endpoints to an in-memory list capped at 256 entries; a
configured seed is still required to bootstrap. Desktop startup uses the
shared peer manager for CYP2 discovery and multi-peer catch-up by default.
CYB1 remains a temporary explicit fallback for diagnostics.

The first optional Storage transfer slice uses HELLO capability `CAP_STORAGE`
and message types 21–27. A peer with that capability can accept one bounded
encrypted chunk, commit a public manifest, and return a committed manifest or
chunk. CYP2 frames remain 4 KiB; larger values are length-bounded and streamed
across data frames with the existing 30-second transfer deadline. The client
checks the network-bound ChunkID and manifest descriptor on retrieval. Storage
is opt-in for `cybou-node serve` through a positive capacity argument; peers
without that argument do not advertise `CAP_STORAGE`. The client-side
`StoragePlacement` provider can fan out to up to three distinct already-
connected storage peers with abort support and reports manifest acknowledgment
counts. The protocol still has no lease negotiation or durability proofs; see
`11_STORAGE_OBJECTS.md` for the current boundary.

CYBOU uses one P2P fabric for protocol propagation.

## Traffic

```text
blocks
headers/finality data
transactions
MailTx
PaymentTx
IdentityTx
validator/consensus messages
peer discovery
```

Email does not create a separate P2P messaging stack.

A MailTx is propagated like another native CYBOU transaction.

## No Email relay role

Do not implement a dedicated relay/rendezvous/mailbox service for CYBOU Email.

Normal P2P transaction propagation brings MailTx to validators and peers.

The recipient obtains finalized mail by normal state/block synchronization.

## Beta Storage data plane

Beta Object Storage requires a bounded data-transfer protocol and provider
roles for placement, leases, audits, repair, and retrieval. These are not live
in the current DEV runtime and must meet `81_BETA_PRODUCT_SCOPE.md` before Beta.

Those must remain integrated with the same identity/security architecture rather than becoming an unrelated second network.
