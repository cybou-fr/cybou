# Peer-to-peer transport target

## Uniform Full Node invariant

CYBOU defines exactly one network node type: Full Node. Every Full Node
implements the complete CYBOU P2P baseline: blocks, announcements,
discovery, operation relay and encrypted storage. There
is no capability bitmap and no network role announcement. Storage is intrinsic;
capacity is local policy. Bootstrap is only a known locator of an ordinary Full
Node. PoA is
possession of the private key matching the public key in genesis, with durable
signing safety. IP, endpoints, TLS sessions, StorageId and peer declarations
never confer consensus authority. StorageId is proven on demand only for a
storage relationship. Peer sync completion is a liveness/UX hint, never proof
of global freshness or a prerequisite for creating an Identity.

Status: **Active P2P transport specification**.
This document defines CYBOU P2P transport, peer discovery, direct mesh topology,
block synchronization, candidate operation relay and storage transfer.

---

## 1. Network topology

The direct observation extension in DEC-289 and
[`NETWORK_OBSERVATION_REPORTS.md`](NETWORK_OBSERVATION_REPORTS.md) is a normative
contract with implemented direct transactions, not a deployed observation service.
Source accepts codes 27/28 for fixed 64/191-byte requests/replies on existing
admitted TLS mesh sessions. The reply copies a five-second runtime cache;
request/session challenge and shared per-IP/global limits follow DEC-289.
Optional observation transactions use a two-second session-owner deadline;
the guard pending ceiling remains five seconds with earlier owner cleanup.
No automatic polling or report consolidation is connected yet. No reports are relayed and no
capability/role/NodeID or PoA route is announced. Implement its exact layout,
request/session binding, rate limits, expiry and partial address-group scope
before enabling automatic polls through the coordinated software-upgrade gate.

CYBOU runs over a direct P2P mesh:

- **Initial discovery**: Nodes connect to the known official bootstrap rendezvous endpoint to discover active peers.
- **Bootstrap role**: Bootstrap is an ordinary CYBOU full peer running the same executable and CYBOU P2P protocol. It has no special consensus role, and is not a traffic intermediary.
- **Direct mesh**: Discovered full nodes establish direct CYBOU P2P connections with each other.
- **Every node listens** (DEC-287): desktops, headless nodes and the bootstrap accept inbound peers
  (default 29461, any free port when taken) and announce that port in HELLO. A node passes on in
  `GET_PEERS` both the peers it dialed and the peers that dialed it, the latter only after it
  connected back to the announced address. A node behind NAT without port forwarding fails that
  check, stays outbound-only and is never advertised. No node advertises the PoA key.
- **Trust**: Network identity is pinned by the compiled Network Public Key (`NetworkID`). Genesis is signed offline by the Network Private Key. PoA finality is proved by the genesis-authorized PoA key.
- **Sovereign admission**: Public inbound and outbound P2P connections are strictly restricted to French IP space, failing closed on missing Geo data. See [`37_FRANCE_SOVEREIGN_NETWORK_POLICY.md`](37_FRANCE_SOVEREIGN_NETWORK_POLICY.md).

CYBOU P2P runs over TCP protected by TLS 1.3 with the post-quantum `X25519MLKEM768`
key exchange group. Plaintext fallback is prohibited.

## 2. Finalized block synchronization

Full nodes announce and gossip finalized blocks across the mesh.
Every receiving node independently validates the block structure, hybrid PoA certificate,
all operation state transitions, and recomputed state root.
Only verified finalized blocks advance canonical local state.

`GET_BLOCKS(first_height:u64, max_count:u8)` requests up to 32 consecutive
blocks. Each response is `BLOCK_META(height:u64, size:u32)` followed by bounded
`BLOCK_DATA` frames. `BLOCKS_END(actual_count:u8)` terminates the batch; the
count must exactly match the received blocks. Heights must be consecutive and
each encoded block is independently executed and verified before commit.
There is no inventory round trip. `BLOCK_ANNOUNCE` offers one height and BlockID;
the receiver pulls that block through the same GET_BLOCKS path.

## 3. Operation relay

There is no distributed mempool. Operations propagate hop-by-hop across ordinary peers:

```text
every full node:
    receives
    verifies encoding, Identity signatures and authorization
    independently executes the candidate against its finalized state
    accepts or rejects locally
    relays only accepted candidates
```

Origin retains the exact signed operation until finality. Each node keeps
accepted candidates in one bounded volatile pool; a PoA node produces blocks
from that same pool. There is no distributed mempool and no canonical pending state.

Origin submission and relay share `OP_META(size:u32, work_nonce:u64)` (DEC-273), bounded `OP_DATA`
frames, and `OP_RESULT(status:u8, OperationID:32)`. `OP_POLL` asks a peer for one
queued operation; an OP_META size of zero is the empty-pool response. Both
receiving paths apply the same ingress budget before allocating payload bytes
and execute the same exact signed operation against local finalized state.
A successful OP_RESULT records delivery to that session only. The candidate
remains available to other sessions until it is finalized or becomes locally
invalid. A session skips candidates it already acknowledged; reconnecting starts
fresh delivery bookkeeping. Failure preserves the candidate for retry. No second
acknowledgment exchange exists.

Relay works in both directions on every session a node opened itself: it
polls the peer (`OP_POLL`) and also pushes its own undelivered candidates to
it (unsolicited `OP_META`). A node behind NAT accepts no connections, so nobody
can poll it; pushing over its outbound sessions is what carries its candidates
to the rest of the mesh and to the PoA.

- Every Full Node accepts and relays locally valid candidates.
- A rejected candidate is never relayed.
- Loop suppression uses a bounded seen-ID cache; finalized operations are purged.
- Acknowledgments between relays are hop-by-hop notifications, never guarantees of finality.

---

## 4. Operation evidence

Operations carry no third-party signatures. Each node relies only on its own
execution and on PoA-finalized blocks (DEC-284).

## 5. Storage chunk transport

Every Full Node implements storage with an explicit local capacity
`V >= 15 GiB` (default 15 GiB); provider obligations are bounded by `floor(2V/3)`.
Smaller values and zero are confined to memory-only unit tests. Low free space rejects new admission while preserving other services.
The ordinary handshake contains no StorageId. Before storage interaction,
`STORAGE_PROOF_REQUEST` challenges the remote storage key; `STORAGE_PROOF` binds
that key to both HELLOs, the TLS exporter and the fresh challenge. StorageId
is a storage replica identity and confers no consensus authority. A node with an
unlocked Identity appends a `StoragePayoutBinding` to `STORAGE_PROOF`: payout
AccountID, Authorization-key signature (Ed25519 + ML-DSA-44) and a STORAGE-key
proof, both over `BLAKE3(CYBOU/STORAGE-PAYOUT-BINDING || NetworkBinding ||
StorageId || AccountID)`. The requester keeps it only if the STORAGE signature
matches the proven StorageId; the runtime then accepts the payout account only
against that account's current finalized Authorization key.

Providers support:
- `PUT_AUTHORIZED_CHUNK`: accepted only after verifying canonical RootPublication finality and Merkle authorization proof.
  A successful `CHUNK_ADMISSION_RESULT` carries the status byte followed by a
  `StorageReceipt`: the provider STORAGE public key and hybrid signature over
  `CYBOU/STORAGE-RECEIPT || NetworkBinding || PublicationID || ChunkID || size u32 LE`.
  The requester rejects a success without a receipt from the proven StorageId.
- `GET_CHUNK_BY_ID`: serves stored encrypted bytes keyed by BLAKE3 ChunkID.
- `GET_CHUNK_AUTHORIZATION_PROOF`: returns Merkle audit path for application state rebuild.
- `STORAGE_AUDIT_CHALLENGE` (25): `ChunkID || offset u64 LE || nonce[32]`.
  `STORAGE_AUDIT_RESPONSE` (26) is `0` when no admitted copy exists, or
  `1 || BLAKE3(bytes[offset..offset+64] || nonce)` computed from the exact
  admitted ciphertext. Local cache never answers audits.

Storage PUT, GET and proof work have separate request limits, with shared per-IP
byte limits of 32 MiB/second and 512 MiB/minute. PUT reserves declared bytes
before allocating or reading the chunk. GET/proof reserve a metadata-only size
bound before reading stored bytes. Active storage requests are bounded to two
per IP and eight per node. A transfer allows 10 seconds setup plus its size at
16 KiB/s, capped at 120 seconds, and fails after five seconds without progress.
These are local abuse limits, never consensus accounting.
