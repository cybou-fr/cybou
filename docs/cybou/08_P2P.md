# Peer-to-peer transport target

CYBOU uses a peer-to-peer transport for finalized block synchronization and
content retrieval. Transport discovery is not a trust anchor: every full node
verifies finality, operation authorization, state execution, and state roots
independently.

## Block synchronization

Nodes exchange bounded announcements and request canonical finalized block
data. A peer may help locate data but cannot make it valid. A node commits a
block only after the PoA proof and deterministic state transition pass local
validation. The finality format and trust model are defined in
`POA_FINALITY.md`.

## Operation submission

Unfinalized operations and chunks remain local to their origin and designated
finalizer. A client may submit an operation directly or use a transparent
relay that does not retain it as network state. The network does not gossip a
distributed pending-operation pool. If the finalizer is offline, the client
keeps the exact candidate and encrypted chunks locally for retry.

## Content retrieval

After finality, clients discover RootPublication operations in finalized
blocks. They identify capsules they can open, then request encrypted chunks by
full BLAKE3 ChunkID from any available providers. Each returned chunk is
verified against its address before decryption; the client discovers child
references only inside decrypted canonical-CBOR nodes.

Providers accept a chunk only when its bytes hash to the supplied ChunkID and
an inclusion proof links it to a RootPublication in their own canonical
finalized history. The publisher sends the operation ID, ChunkID, leaf index,
Merkle siblings, and stored-byte length in `PUT_AUTHORIZED_CHUNK`, followed by
bounded `AUTHORIZED_CHUNK_DATA` frames. No finality certificate or public
manifest is sent with the request. `GET_CHUNK_BY_ID` requests use only the full
ChunkID; successful responses stream `CHUNK_DATA` frames. The transport profile
is CYP2 wire version 2. Provider admission and durability requirements are
defined in `STORAGE_ADMISSION.md`.

Only the content-addressed chunk API is supported. Legacy `StorageObject`,
indexed-manifest operations, and their wire message IDs have been removed; the
reserved old IDs are rejected. Desktop provider selection and transfer calls
still need migration to the current API.

## Resource and trust rules

- Bound frame size, request concurrency, tree depth, chunk count, and caller-limited total
  reconstructed bytes.
- Treat peer-provided addresses and discovery responses as hints only.
- Do not expose AccountID, filenames, MIME types, paths, or graph edges in
  content transport metadata.
- Do not equate a successful peer response or finalized publication with
  durable availability.
- Use the same canonical serialization and validation rules on every platform.

This is the active transport profile. Its current chunk API is implemented in
source; desktop transfer integration and Beta durability remain open. See
`26_IMPLEMENTATION_STATUS.md`.
