# 08 — P2P network

Implementation status: the native DEV runtime uses a bounded TCP endpoint for
finalized-block retrieval and one-operation submission. A separate native
`src/cybou/p2p/` session layer now has bounded frames, a persistent TCP
connection, HELLO with NetworkID/finalized height/tip/capabilities, and
PING/PONG. HELLO advertises block-serving and operation-acceptance capabilities;
the session checks them before requests or service. It rejects wrong-network
peers and limits each read/write to five
seconds. An outbound peer manager now uses the runtime's verified NetworkID and
finalized status to maintain up to eight explicitly configured, persistent
sessions, reject duplicate endpoints, and drop peers that fail a health ping.
The DEV producer can now listen on a separate CYP2 port. `p2p-probe` checks
health and `p2p-sync` retrieves finalized blocks through one persistent
connection, using bounded 4 KiB frames and a 32 MiB/30-second transfer limit.
The 30-second deadline covers the full request/response on the client and the
full block send on the producer, including every chunk.
`p2p-follow` keeps an observer connected to one explicit peer, polls for new
blocks, and retries after a transport disconnection. It stops on a failed
handshake or block verification.
`p2p-follow-peers` accepts up to eight explicit numeric endpoints, tries other
peers when one is unavailable, and excludes a peer after handshake or block
verification failure. Malformed frame headers, invalid block metadata, and
invalid chunks also exclude that peer. A connection that closes or times out
during a transfer is retried as temporarily unavailable. A peer that closes
before HELLO is retried; a malformed HELLO frame or a valid HELLO with the
wrong NetworkID is rejected. HELLO must contain a nonzero tip; at height zero
that tip must match the trusted genesis block ID. If a local historical block
exists at the height announced in HELLO, its ID must match the announced tip.
The same trusted-chain check applies before the listener serves an inbound peer.
Every accepted block still passes local finality and state checks. At the
height advertised in HELLO, the received finalized block
must also match the peer's advertised tip. This is manual peer configuration,
not discovery or gossip.
If a peer reports no block at a height it advertised in HELLO, the observer
disconnects and retries it later while trying other peers. A genuine missing
next block beyond the advertised height keeps the session open.
The observer commits each block only after canonical state and BFT finality
verification. CYP2 can also submit one canonical operation (up to 128 KiB)
in bounded frames within a 30-second send/acknowledgment deadline and return a
checked OperationID and admission status.
Admission is not finality. The DEV listener handles up to eight concurrent
incoming sessions with one bounded worker per peer; excess connections close.
NodeRuntime now owns a manager when a CYP2 endpoint is configured; operation
submission and finalized-block sync then use that session. The Qt desktop
can opt into this transport with explicit DEV host/port environment settings.
The default compiled bootstrap still points to its available CYB1 endpoint.
TCP connection setup now has a five-second deadline. A
compiled-in DEV bootstrap address locates the authority but supplies no
consensus trust. Peer discovery, operation gossip, block gossip, and multi-validator
consensus transport remain targets.

CYBOU uses one P2P fabric for protocol propagation.

## Traffic

```text
blocks
headers/finality data
transactions
MailTx
PaymentTx
IdentityTx
validator/consensus messages
peer discovery
```

Email does not create a separate P2P messaging stack.

A MailTx is propagated like another native CYBOU transaction.

## No Email relay role

Do not implement a dedicated relay/rendezvous/mailbox service for CYBOU Email.

Normal P2P transaction propagation brings MailTx to validators and peers.

The recipient obtains finalized mail by normal state/block synchronization.

## Future Storage

Object Storage may introduce its own data-transfer protocols and provider roles later.

Those must remain integrated with the same identity/security architecture rather than becoming an unrelated second network.
